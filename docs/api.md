# API conventions

## Surface

All application endpoints are under `/api/v1`. OpenAPI is generated by FastAPI and is a contract artifact; breaking changes require a new API version or an explicit migration window.

Release `0.5.0` exposes:

- `GET /api/v1/health`: process liveness and non-secret build/environment metadata.
- `GET /api/v1/ready`: PostgreSQL connectivity; returns a safe HTTP 503 envelope when unavailable.
- `POST /api/v1/auth/register`: create an identity and initial rotating session.
- `POST /api/v1/auth/login`: authenticate with generic failure responses and persistent throttling.
- `POST /api/v1/auth/refresh`: rotate an opaque refresh token; replay revokes its replacement chain.
- `POST /api/v1/auth/logout`: revoke a refresh-session chain; repeated/unknown tokens remain safe.
- `GET /api/v1/auth/me`: read the authenticated profile.
- `POST /api/v1/accounts`: idempotently create an account owned by the authenticated user.
- `GET /api/v1/accounts`: list owned account balance projections, optionally filtered by status and `as_of`.
- `GET /api/v1/accounts/{account_id}`: read one owned account projection.
- `GET /api/v1/accounts/{account_id}/balance`: read its ledger-derived balance and version.
- `PATCH /api/v1/accounts/{account_id}`: update metadata or perform an audited lifecycle transition with optimistic concurrency.
- `GET /api/v1/categories`: list active owned categories, optionally including archived entries.
- `POST /api/v1/categories`: idempotently create an owned category.
- `PATCH /api/v1/categories/{category_id}`: idempotently rename, recolor, reparent, archive, or restore an owned category.
- `GET /api/v1/tags`: list active owned tags, optionally including archived entries.
- `POST /api/v1/tags`: idempotently create an owned tag.
- `PATCH /api/v1/tags/{tag_id}`: idempotently rename, recolor, archive, or restore an owned tag.
- `POST /api/v1/transactions`: idempotently create an expense or income draft.
- `GET /api/v1/transactions`: list owned transactions with status, type, account, category, tag, and occurred-at filters.
- `GET /api/v1/transactions/{transaction_id}`: read one owned transaction.
- `PATCH /api/v1/transactions/{transaction_id}`: idempotently edit a draft.
- `POST /api/v1/transactions/{transaction_id}/post`: idempotently post a draft to the authoritative ledger.
- `POST /api/v1/transactions/{transaction_id}/reverse`: idempotently create a linked reversal for a posted transaction.
- `POST /api/v1/transfers/preview`: calculate linked account impacts and a source-balance fingerprint.
- `POST /api/v1/transfers/commit`: atomically post the transfer pair and optional fee using the reviewed fingerprint.
- `GET /api/v1/transfers/{transfer_id}`: read one owned transfer and all canonical movements.
- `POST /api/v1/accounts/{account_id}/reconciliations/preview`: compare an effective-time ledger balance with the entered actual balance.
- `POST /api/v1/accounts/{account_id}/reconciliations/commit`: atomically post one neutral adjustment and reconciliation record.
- `POST /api/v1/reallocations/preview`: derive same-currency Keep Total Fixed targets and balancing-account residual.
- `POST /api/v1/reallocations/commit`: atomically post immutable session/line records and all required internal transfer pairs.
- `POST /api/v1/people`: idempotently create an owned counterparty.
- `GET /api/v1/people`: list owned counterparties, optionally including archived rows.
- `PATCH /api/v1/people/{person_id}`: update or archive a counterparty with optimistic concurrency.
- `POST /api/v1/debts`: atomically create an existing, lend-now, or borrow-now receivable/payable position.
- `GET /api/v1/debts`: list owned debts by person, status, or direction.
- `GET /api/v1/debts/{debt_id}`: read a debt with its canonical origin movement and repayment history.
- `POST /api/v1/debts/{debt_id}/payments`: atomically post a repayment movement and reduce the debt.
- `POST /api/v1/debts/{debt_id}/cancel`: cancel an unsettled debt with an audit reason.
- `POST /api/v1/transactions/{transaction_id}/shares`: create one recoverable share and linked receivable debt.
- `GET /api/v1/transactions/{transaction_id}/shares`: list recoverable shares for an owned expense.
- `PATCH /api/v1/shared-expense-shares/{share_id}`: update or cancel a recoverable share under the gross-expense cap.
- `POST /api/v1/transactions/{transaction_id}/refund`: post a linked refund inflow without exceeding the unrefunded expense amount or its shares.

Later milestones add `/merchants`, `/products`, `/analytics`, `/media`,
`/recurring`, and `/goals` in roadmap order.

Authenticated endpoints derive ownership exclusively from the bearer token. They
do not accept an authoritative `user_id`, and an account owned by another user is
indistinguishable from a missing account.

## Money representation

```json
{
  "amount": "100.0000",
  "currency": "MAD"
}
```

JSON numbers are not accepted for money. This prevents clients from introducing binary floating-point values before validation.

## Errors

All expected errors use one envelope:

```json
{
  "error": {
    "code": "NEGATIVE_BALANCE_NOT_ALLOWED",
    "message": "The operation would take the account below its allowed balance.",
    "details": {"account_id": "..."},
    "request_id": "..."
  }
}
```

Messages are safe for users. `details` contains structured, non-sensitive repair hints. Unknown failures return `INTERNAL_ERROR` without stack traces or private data.
Framework 404/405 responses, request validation failures, domain errors, and
readiness failures use the same envelope. Every response includes `X-Request-ID`;
a valid caller-supplied request ID is echoed, while an invalid one is replaced.

## Idempotency

Balance-affecting POST endpoints require:

- `Idempotency-Key`: UUID generated once for the business operation.
- `client_operation_id`: the same stable UUID in the request body.
- Canonical request hashing on the server.

Retries with the same key and body return the original status/body. Reuse with a different body returns HTTP 409 and `IDEMPOTENCY_CONFLICT`.

The coordinator and PostgreSQL constraints implement this behavior and commit the
business effect, audit event, and stored response atomically. Financial-group
idempotency records remain durable for the lifetime of the user profile. Account creation,
catalog mutations, and every transaction mutation use this protocol. Financial
create, reverse, debt, repayment, share, and refund requests also carry
`client_operation_id` in the body; it must
match the header. Update and post scopes are bound to the transaction in the URL.

## Core transaction lifecycle

- Creating or editing a draft never changes an account balance.
- Posting validates ownership, account state and currency, category compatibility,
  tag state, occurrence time, and negative-balance policy while locking the account.
- Posted financial fields and tag links are immutable in PostgreSQL.
- A correction creates an opposite, linked posted transaction and marks the
  original `REVERSED`; direct deletion or rewriting is not supported.
- The server response is the canonical financial state. Clients may display
  pending operations but must not invent projected balances.

## Optimistic concurrency

Metadata updates carry `version`. Stale versions return HTTP 409 `VERSION_CONFLICT`.

Preview/commit workflows return a deterministic source fingerprint bound to the relevant account versions and balances. Commit recalculates under account locks; a stale fingerprint returns `STALE_BALANCE`, and the client must refresh and ask the user to confirm again.

## Pagination and time

- The Milestone 2 transaction list uses bounded `limit`/`offset` pagination with
  deterministic `(occurred_at, id)` ordering. Cursor pagination remains the target
  for larger collections.
- Timestamps are RFC 3339 UTC strings.
- Date grouping accepts an IANA timezone and defaults to the authenticated user's configured timezone.
